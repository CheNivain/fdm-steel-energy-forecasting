# Final-System Architecture and Tests

## Assignment coverage

Stages 9 and 10 require model integration, consistent preprocessing, input
validation, meaningful results and a working frontend/backend. This system
implements those through a local FastAPI service and browser dashboard.
The technical report and presentation remain separate submissions.

## Components

```text
Browser: index.html + app.js + rolling.js + styles.css
  |
FastAPI: main.py -- schemas, uploads, exports, errors
  |-- service.py -- original model, historical replay, development evidence
  |-- rolling.py -- forecast cursor, provisional history, actual reconciliation
  |      |-- features.py -- ordered causal features from the preceding 672 rows
  |      |-- deployment.py -- fixed-setting Random Forest refit on actuals
  |      |-- app_data/deployment/ -- saved versions and atomic active manifest
  |-- storage.py -- SQLite connections and legacy replay storage
  |
SQLite -- actual readings, immutable forecast payloads, corrections, imports
```

One server process, one worker, bound to 127.0.0.1. The frontend uses local
Chart.js and Lucide assets; it requires no Node server or CDN. Database values
use parameterized SQL. Model inputs and displayed values are not generated by
browser-side formulas.

## Model lifecycle

The earlier verified artifact in random forest/outputs_advanced/ remains the
development/replay model. Its saved test predictions and metrics are preserved.

The production copy uses the same selected configuration and 70-feature pipeline.
Its initial fit uses 33,695 complete examples from the 35,040 original readings.
The seven-day warm-up and the known invalid target/window are excluded.
The raw dataset remains unchanged. No future-value interpolation is introduced.

Training and runtime inputs are checked against one another. Forecasts learn
the delta from the preceding interval and are floored at zero by the pipeline.
The selected transformer ignores load_level; no future load category is needed.

Model files use unique names. SHA-256 and scikit-learn version are checked on
load. The current manifest is replaced atomically after serialization. Existing
artifacts remain available. A manual background refit uses all accumulated actual
readings with the fixed chosen settings; it never uses recursive predictions
as training targets. Imports are blocked until the refit finishes. Forecasting
can use the prior model during the fit; deployment promotion waits for the
forecast lock, invalidates provisional input history and increments its revision.

A successful refit is not an accuracy evaluation. Old test metrics do not apply
to the refitted model or recursive chains. Fresh measured outcomes are needed.

## Rolling state and consistency

The default workspace seeds all original readings and flags the known invalid
measurement. It treats timestamps as interval ends under the team's original
midnight +1 day assumption. Its first unknown interval is 1 Jan 2019, 00:00-00:15.

Each prediction uses the preceding 672 values. The result is stored separately
from actuals; recursive input counts, horizon, model hash, history hash and
the exact 15 input features are retained. Requests for later times generate
the necessary intervening intervals. One request is bounded to 672 generated
intervals; requested output is 15 or 30 minutes.

A workspace revision rejects stale concurrent requests. Request IDs make retries
idempotent. All generated intervals are committed in one transaction, so a failed
batch does not partly advance. A process-local lock serializes mutations; run
one worker only.

Actual uploads validate dates, cadence, units, counts, duplicates and gaps.
An upload can add measurements or explicitly correct existing ones. Corrections
have an audit record. Incoming actuals invalidate the active provisional history
and reset the cursor to the latest actual; previously issued predictions remain
immutable for comparison. The current implementation intentionally does not
recompute past forecasts silently.

Comparison joins forecasts to actuals by interval-end timestamp. It scores the
first issued prediction once per interval, with separate measured-history and
recursive subgroups. High-load MAE always uses actual >=50 kWh. A missing high-load
subset has a null score, never zero. Changing operational alerts does not change
the evaluation cutoff.

## Main API

| Method/path | Purpose |
| --- | --- |
| GET /api/workspace | Cursor, actual history, model/refit status, reconciled metrics |
| POST /api/workspace/forecasts | Requested start, 1/2 intervals, threshold, revision, request ID |
| GET /api/workspace/forecasts | Latest 500 records, actuals and errors |
| GET /api/workspace/forecasts/export.csv | Entire rolling ledger |
| POST /api/workspace/actuals | Multipart ISO interval-end CSV plus explicit correction flag |
| POST /api/workspace/reading | One actual interval reading |
| GET /api/workspace/actuals/export.csv | Stored readings and verification flag |
| POST /api/workspace/train | Start measured-data-only background refit |
| GET /api/workspace/template.csv | Blank actual-upload header, no invented measurements |
| GET /api/model | Original development metrics, settings and five reported results |
| GET /api/datasets | Seven historical samples plus standalone uploaded replay histories |
| POST /api/forecasts | Legacy next-interval replay/standalone prediction |
| GET /api/evaluation | Recorded development test day |
| GET /api/openapi.json | Full schema, including retained legacy routes |

Legacy replay imports require 672-40,000 readings. Actual updates allow 1-40,000.
Both use an 8 MB per-file limit; accumulated operational history is retained.
All energy readings are kWh per interval, never cumulative meter totals.

## Verification commands

```bash
.venv/bin/python -m unittest discover -s tests -v
```

Rolling tests exercise first-interval alignment, estimated lag reuse, an evening
jump, original-prediction reconciliation, corrections, gaps, replayed requests,
stale clients, atomic failure, persistence, first-issued scoring and causal
training/runtime feature equivalence. Existing development and application tests
cover input validation, metrics, saved-model outputs and legacy workflows.

For browser QA, use an isolated database and the deployment artifact:

```bash
FDM_APP_DB=tmp/browser-check.sqlite3 FDM_MODEL_DIR=app_data/deployment .venv/bin/python run_app.py --port 8003
# In a second terminal with Playwright available:
FDM_TEST_URL=http://127.0.0.1:8003 node tests/browser_rolling.cjs
```

Use a fresh QA database for each complete run; never delete a user's database.
The script adds a clearly named synthetic QA actual for reconciliation.
Set CHROME_PATH when Chrome is installed at a different location.
No Playwright dependency is needed to run the delivered application.

Browser checks cover the real deployment artifact, repeated forecasting,
30-minute totals, actual reconciliation, errors, JSON/CSV export, seven weekdays,
five-model evidence, persistence, chart pixels, and every screen at 320/390/768/1024 px.
Screenshots and a machine-readable result are in tmp/final-system-qa/.
The original tests/browser_smoke.cjs covers the legacy replay workflow.

## Boundaries

- Local academic system; no live meter feed or public authentication.
- Historical timestamps are an explicit scenario, not present-day machine observations.
- Monthly actual updates leave long recursive chains; accuracy can degrade or flatten.
- No proven prediction interval, automated machinery control or guaranteed savings.
- Dataset timestamp interpretation must be confirmed before real deployment.
- Original model scores retain their documented preprocessing limitations.
- KNN and Gradient Boosting use different test periods/cutoffs; no fair five-way
  winner has been established from those reported tables.
- Host/origin checks, escaped UI text and spreadsheet-formula-safe CSV exports are used.
- Uploaded files are parsed as data, never loaded as arbitrary model/pickle files.
- Restarts during training leave the last complete manifest available; rerun an
  interrupted refit explicitly. There is no distributed job scheduler.
- Include code, model artifacts, data approval, report, presentation and honest
  contribution/assistance acknowledgements in the final submission.
